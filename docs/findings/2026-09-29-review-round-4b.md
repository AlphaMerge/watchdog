## `N-18` — A webhook subject outside Latin-1 fails the delivery for ever

### A generic webhook alarm fails to send, and never succeeds on retry, when its rendered subject has any character above U+00FF

- **Severity:** high (both verifiers). **Category:** correctness. **Introduced in:** `20bcaab`, at `packages/core/src/notifications/delivery/webhook.ts:77`.
- **Scenario.** An operator sets up a generic webhook template whose subject is "%sensor on %device: %lastmessage". Three inputs each break it: a device named in Cyrillic or CJK, a sensor name with an emoji, or a Down message from the system's own sensors containing an em dash (dns-blocklist: "that zone does not exist — check the spelling"). A placeholder that resolves to '—' (%lastvalue with no value, %previousstate with none) does the same. The subject is rendered unescaped and goes into the x-ms-subject header with only CR and LF removed. Node's http.request only accepts header values made of \t, 0x20-0x7E and 0x80-0xFF, so it throws ERR_INVALID_CHAR synchronously. GuardedHttpClient catches that and returns { ok:false, retryable:true }. The delivery loop retries the same subject until it gives up. The alarm never reaches the endpoint. A test send with ASCII example values passes, so the operator does not find out at setup. P-151 named this exact path ("x-ms-subject carries a rendered subject with whatever characters a sensor name has") but only fixed the timer crash, so the failure itself is still there.
- **First verifier.** The path holds at 20bcaab. headerSafe only replaces CR and LF. Node's ClientRequest constructor runs setHeader, and so validateHeaderValue, on every entry of options.headers, and rejects anything outside \t, 0x20-0x7E and 0x80-0xFF with ERR_INVALID_CHAR, synchronously. http-client.ts's own P-151 comment says so. The throw rejects #exchange, and send() maps it to { ok:false, retryable:true }, so every retry renders the same subject and fails again. Inputs that trigger it: any sensor, device or group name above U+00FF (Cyrillic, CJK, emoji), and two built-in placeholders that the system itself resolves to U+2014: %laststatus when there is no previous state and %lastvalue when there is no reading. Nothing stops it upstream. render() leaves the subject unescaped (escaping 'none'), the template save validates only placeholder names, and webhook templates are never summarised, so the dispatcher's immediate path is the only path. The claim that a test send passes is only partly right. The example context has lastValue null, so a subject that uses %lastvalue fails the test send too. With ASCII names and no %lastvalue, the test send passes and the real alarm fails. Not in round 4 or any open ticket. P-151 fixed only the timer crash. The one webhook test (webhook-delivery.test.ts:269) uses an ASCII subject.
- **Second verifier.** Walked from the dispatcher to the header. Nothing stops a character above U+00FF. headerSafe (transport.ts:94-96) only folds CR and LF. WEBHOOK_METHOD's settingsSchema (methods.ts:134-170) and the template save (templates.ts:672-685) check only placeholder names, not the subject's characters. The web UI shows the Subject field for every method (TemplatesView.tsx:268-274). Its default subject for a new template is '%sitename: %sensor on %device is %status' (templates-model.ts:25), so the default webhook template already puts operator-chosen names into x-ms-subject. With a Cyrillic or CJK site name, every webhook alarm fails. The code admits the failure: http-client.ts:205-215, the P-151 comment, says http.request throws ERR_INVALID_CHAR synchronously for this exact header. P-151's outcome in TASKS.md:15745-15757 fixed only the timer crash, and its test used a bad secret-header name, not a subject. No later commit touches webhook.ts, http-client.ts or transport.ts (git log 20bcaab..HEAD is empty for them). The retry renders the same subject every time, so the delivery can never succeed. That is lost alarms in ordinary use for any install whose site, device, group or sensor names are outside Latin-1, so I kept high. It is not a round-4 ticket and not a decision.
- **Trace.** dispatcher.ts:213-217 render({subject: t_subject}, context, escaping) -> placeholders.ts:121 '%laststatus' => previousState ?? '—' / :133 '%lastvalue' => '—' / sensor, device and group names as stored -> dispatcher.ts:237-246 #attempt(transport, {subject: rendered.subject}) -> webhook.ts:77 headers {'x-ms-subject': headerSafe(message.subject)} -> transport.ts:94-96 headerSafe = replace(/[\r\n]+/g,' ') only -> http-client.ts:111-124 #exchange(..., headers: {...request.headers}) -> http-client.ts:238-252 send(target, {headers: {..., ...options.headers}}) throws ERR_INVALID_CHAR synchronously inside the Promise executor -> rejection -> http-client.ts:125-127 catch => { ok:false, retryable:true, error } -> dispatcher.ts:248 #record(attempts+1, result) -> retried with the same subject until attempts run out
- **Suggested fix.** In webhook.ts, encode the subject so it survives as a header value. Put the rendered subject's UTF-8 in x-ms-subject percent-encoded (encodeURIComponent) whenever it contains a character outside printable ASCII, and flag that with x-ms-subject-encoding: utf-8-percent. Leave a pure-ASCII subject as it is today. The alternative is to fold anything outside \x20-\x7E to '?' so the header can never fail the delivery, since the body already carries the full text. Either way, the header must not be able to fail the delivery.
- **A test that would have caught it.** webhook-delivery.test.ts: deliver through the real GuardedHttpClient to the local test server with a template subject of '%sensor on %device: %laststatus', where the device is named 'Київ-edge' and the sensor has no previous state. Assert ok:true, that the server received the request, and that the decoded x-ms-subject round-trips to the rendered text. Before the fix the result is ok:false, retryable:true, with ERR_INVALID_CHAR.

## `A-48` — A program template's secret arguments follow a change of its visible arguments

### A program template's secretArgs carry over an edit that changes the visible args telling the program where to send them

- **Severity:** medium (both verifiers). **Category:** security. **Introduced in:** `f541bd5`, at `packages/core/src/notifications/methods.ts:253`.
- **Scenario.** An administrator sets up a program template: path "send-sms.sh", args ["--gateway","https://sms.example/api","--to","+100"], secretArgs ["--key","<api-key>"]. A template editor holds write on templates but has never seen the key. They PUT /templates/:id with the same path, args ["--gateway","https://attacker.test/api","--to","+100"], and no secretArgs. #stays compares only `path`, which is unchanged, so mergeSecrets carries secretArgs. secretsLeftBehind returns [], so the audit entry has no secretsCleared. They then POST /templates/:id/test (WRITES bar). ProgramTransport runs send-sms.sh with [...args, ...secretArgs], and the stored key goes to the editor's gateway. Adding or removing visible args also shifts the positional secret into a different option of the same program. This is the re-pointing A-40 set out to close, through the program method's other destination field.
- **First verifier.** At 20bcaab the program method binds secretArgs to `path` only. A PUT that changes `args` and leaves out secretArgs therefore carries the stored secretArgs over, no secretsCleared is recorded, and a test-send runs the admin's program with the editor's new visible args followed by the stored secret. Nothing else stops this: the args schema allows any strings, the route bar is WRITES (any readwrite account), and test-send uses the stored, merged settings. The ticket's literal example names only `path`. But its Done-when says a writer who re-points a template and tests it has a receiver that sees no secret, and the outcome's governing rule is that a secret carries over only while every setting saying where it goes is unchanged. The same commit binds exe.script's secret to its arguments for exactly this reason: 'a script that takes its target as an argument is the common case'. A program whose gateway or host is a visible argument is the same shape, so the decision is not met for this method. This is not A-44, which covers stderr echo, and it is not A-41 or A-42. Kept at medium: it needs an admin-installed program that takes its destination from args (the case A-40 itself calls common) and a readwrite account, and the leaked value is a stored write-only secret. Adding or removing a visible arg also shifts a positional secret into a different option.
- **Second verifier.** I went looking for anything that stops this and found nothing. The only binding is `secretDestinations: { secretArgs: ['path'] }` (methods.ts:253). `#stays` (methods.ts ~457-468) compares only the declared fields, so a PUT that changes `args` and leaves out `secretArgs` carries the stored secret over (mergeSecrets ~417-434). secretsLeftBehind returns [], so the audit entry has no secretsCleared. The args schema allows any strings (up to 2000 chars each). The only test is templates.test.ts:192-198 ('binds a program's secret arguments to the program'). It checks path only; no test asserts either that changed args keep the secret or that they clear it. The PUT route description (routes/templates.ts ~560) and the TemplateService.update comment name only 'a program's path', so the literal A-40 decision covers path alone. But A-40's Done-when ('a writer who re-points a template and tests it has a receiver that sees no secret') and its one governing rule ('every setting that says where it goes') are not met. The same ticket binds exe.script's secret to its arguments 'because a script that takes its target as an argument is the common case', and a program method is the same shape. It is not A-44 (stderr echo), A-41 or A-42, and it is not in round 4. c390d5e, the only later commit, does not touch this code. Preconditions that keep it at medium, not high: the program method is off until an operator sets notifications.program.directory, and the admin's program must take its destination or recipient from a visible argument. The actor needs a readwrite account (the WRITES bar) and never needs to see the secret. The stored secret also reaches the new destination on the next real alarm, not only through /test.
- **Trace.** PUT /templates/:id (packages/core/src/api/routes/templates.ts:550, config WRITES) -> TemplateService.update (packages/core/src/notifications/templates.ts:543) -> #parse -> notificationMethods.mergeSecrets (templates.ts:645) -> methods.ts:417-434 carries secretArgs when #stays is true -> methods.ts:457-468 #stays checks only secretDestinations['secretArgs'] = ['path'] (methods.ts:253), so a changed `args` (methods.ts:251 placeholder content, schema :265-270 free strings) still counts as 'stays' -> templates.ts:555 secretsLeftBehind returns [] (same #stays), so the audit has no secretsCleared -> repo.update stores the new args with the old secretArgs -> POST /templates/:id/test (routes/templates.ts:492, WRITES) -> test-send.ts:134 uses the stored template.settings -> delivery/program.ts:72-76 argv = [...args, ...secretArgs] -> runProgram sends the secret wherever the new visible args point the program.
- **Suggested fix.** Declare `secretDestinations: { secretArgs: ['path', 'args'] }` in PROGRAM_METHOD (methods.ts:253). sameDestination already compares arrays by JSON, so any change to args, including a reorder or an added argument, clears secretArgs unless they are resent. Update the PUT route description (routes/templates.ts:560-563) and the update() doc comment to say 'a program's path or args'.
- **A test that would have caught it.** In the template service or route tests: create a program template with path 'send.sh', args ['--gateway','https://a.test'] and secretArgs ['k3y-value']. PUT the same path with args ['--gateway','https://b.test'] and no secretArgs. Assert that the stored settings have no secretArgs, that the template.updated audit entry has secretsCleared ['secretArgs'], and that a test-send through a program that echoes its argv to a file does not show 'k3y-value'. Add a control case: a PUT with identical args keeps secretArgs. Add a mutation case: dropping 'args' from secretDestinations must fail the test.

## `A-49` — Four answers that still reveal what the reader cannot see

### With ?include=, a restricted caller's tag moves when a hidden ancestor changes, so an unchanged answer tells them a hidden object was edited

- **Severity:** low (both verifiers). **Category:** security. **Introduced in:** `69d1e5a`, at `packages/core/src/api/routes/objects.ts:412`.
- **Scenario.** Operator Bob has read on device D through a direct grant. D's parent group G ("Customer B") is hidden from him, and ?include=ancestors trims it out of his path. Bob polls GET /objects/D?include=ancestors with If-None-Match. An administrator renames G, edits its comments or tags, pauses it (object_pause touches the owner), or rotates a credential set on it (migration 041 touches the owner). G's version bumps, so the chain digest changes and Bob's salted tag changes. He gets a 200 whose body is identical, which tells him an object he may not see was just modified, and when. That is the view-independent tag component A-32 was meant to remove from a restricted caller's validator.
- **First verifier.** With any ?include=, detailTag computes chainValidator(id), which hashes id:version for the object and every ancestor up to the root with no visibility filter. For a restricted caller that digest is folded into the tag through viewedChain. With include=ancestors, service.ancestors(id, visibility) trims hidden ancestors out of the body. A version bump on a hidden ancestor therefore changes the tag and forces a 200 with an identical body. The hidden ancestor may be renamed, have its comments or tags edited, gain a trigger (015 touch_owner), have a credential set written or deleted (002/041), or have a device_config or setting changed. No guard filters the chain, and nothing in A-32, A-12 or round 4 decides it. A-32 addressed only inherited setting sources, which are ids and depths and were decided not to be view-dependent. The oracle is noisy: Bob sees parentId already, so he knows the hidden ancestor exists; a visible ancestor's non-displayed edit also moves the tag, though Bob can rule that out by reading the visible ancestors' own versions; and with include=settings or include=credentials a hidden ancestor's inherited values legitimately appear in the body by design. The residual leak is one bit plus timing about edits to a hidden object that do not otherwise show, such as renames, comments, tags and triggers, and only by polling. The behaviour predates 69d1e5a (S-13), and A-32 took ownership of the restricted tag without closing it. Low.
- **Second verifier.** With any ?include=, detailTag computes chain = validatorFor(object.id) -> repository.ts:677-700 chainValidator. That is a recursive CTE hashing id:version for the object and every ancestor, with no visibility parameter at all. For a restricted caller it is folded into the tag by viewedChain(chain, principal@epoch#childCount) (preconditions.ts). With include=ancestors, the body's path comes from service.ancestors(id, visibility) (service.ts:349-352 -> repo.ancestors), which trims hidden ancestors. A-32's own test (object-visibility.test.ts ~1937-1953) confirms the trim for the watcher account. A hidden ancestor's version moves on a rename, comment or tag edit (object_touch 002:80) and on side-table writes (002:89-146). None of these moves the access epoch, the principal or the visible child count, so the restricted caller gets a 200 with an unchanged body where a 304 was due. I found no filter on the chain, and no ticket or decision covers it: A-32 decided only that inherited setting sources are not view-dependent, round 4 has no ETag item, and c390d5e does not touch this. It is narrow. The caller already learns the hidden parent's id from parentId. With include=settings or credentials, hidden ancestors' values reach the body by design. What leaks is one bit plus a time for otherwise invisible edits (a rename, comments, tags) to a hidden container, learned only by polling, and a visible ancestor's edit adds noise the caller has to rule out. Low. It shares detailTag with admin-etag-misses-childcount, but the cause is opposite (the chain covers too much), so it is not a duplicate. The critic says the same.
- **Trace.** GET /objects/D?include=ancestors (packages/core/src/api/routes/objects.ts:~680) with If-None-Match -> detailTag objects.ts:405-416: :412 chain = await validatorFor(object.id) because include.size > 0 -> objects.ts validatorFor -> service.chainValidator -> repository.ts:~677-700 recursive CTE over every ancestor, md5(string_agg(id:version)) with no visibility -> objects.ts:414-415 view salt (principal@epoch#childCount), then etagFor(version, viewedChain(chain, view)) (preconditions.ts:36-40). Body: sendDetail objects.ts:377 body.ancestors = service.ancestors(id, visibility), trimmed by Visibility.trim (repository.ts:~640-650). A hidden ancestor's version is bumped by object_touch (002:68-82) and object_touch_owner (002:89-146, 015:56, 041:32/40), and epoch/principal/childCount do not change, so the tag changes with an identical body.
- **Suggested fix.** For a caller without visibility.everything, and when the include set holds neither 'settings' nor 'credentials' (the two whose bodies carry hidden-ancestor content by design), compute the chain digest over the object plus only the ancestors visibility.trim keeps. For example, add chainValidator(id, salt, visibility?) that applies the same trim the ancestors read uses before string_agg. All-seeing callers and settings/credentials includes keep the full chain.
- **A test that would have caught it.** In object-visibility.test.ts, as the operator with a direct grant on D whose parent G is hidden: GET /objects/D?include=ancestors and record the ETag. As an administrator, rename G (and separately add a tag or comment). GET again as the operator with If-None-Match set to the recorded tag and assert 304. Then rename a visible ancestor and assert 200, so the visible chain is still covered.

### An all-seeing caller's object ETag does not cover childCount, so a child created or deleted under an object is answered 304 with the old count

- **Severity:** low (both verifiers). **Category:** correctness. **Introduced in:** `69d1e5a`, at `packages/core/src/api/routes/objects.ts:413`.
- **Scenario.** An administrator (visibility.everything) GETs /objects/<device> and gets childCount 3 with ETag W/"7". Someone creates a fourth sensor under the device. Nothing bumps the device's version: object_touch fires only on an UPDATE of the device row, and no trigger touches a parent when a child is inserted or deleted. The A-32 outcome itself says 'creating a sensor moves no epoch, and the count is the one part of the answer that changes with neither the object nor a grant'. The administrator's next GET with If-None-Match: W/"7" gets 304 and keeps childCount 3. The Cache-Control: private, max-age=0, must-revalidate header added by this commit makes a browser send that conditional request by itself and reuse the stale body. The same happens for a child deleted or moved out.
- **First verifier.** For a caller with visibility.everything, detailTag returns etagFor(version, chain), and that tag has no child component. The body's childCount comes from ObjectBase.childCount, a live correlated count. No trigger on object INSERT or DELETE touches the parent. The only triggers on object are BEFORE INSERT/UPDATE validation, object_touch on UPDATE of the row itself, and 052's AFTER UPDATE OF parent_id for the access epoch. Service create and move do not touch the parent either; repository.ts:1475 updates only the moved row. So a child created, deleted or moved in or out leaves the parent's tag unchanged, and a conditional GET with the old tag gets 304, which the browser serves with the stale childCount. Cache-Control 'private, max-age=0, must-revalidate' makes the browser send that conditional request automatically. The A-32 outcome itself says the count 'changes with neither the object nor a grant', and it salts only restricted callers with it. For admins this predates A-32 (S-13 tag), and A-32 explicitly kept 'the tag it always had', resting on the premise that the tag covered the admin's answer, which it does not. Not ticketed and not in round 4. Low: the only stale field is a count, and a full reload corrects it.
- **Second verifier.** For visibility.everything, detailTag returns etagFor(object.version, chain) (routes/objects.ts ~413), which has no child component. The body's childCount is the live correlated count at repository.ts:77, mapped at :130. I checked every trigger on `object` at 20bcaab: 001:102 hierarchy check, 001:133 cycle check, 001:150 and 002:188 set_updated_at, 002:80 object_touch_row (BEFORE UPDATE of the row itself), 052:70 AFTER UPDATE OF parent_id for the epoch. None touches the parent on a child INSERT or DELETE. object_touch_owner (002:89-122) touches the side table's own object, never its parent. The only UPDATE object statements in src (repository.ts:781 sibling order, :1417 own row, :1475 reparent) do not touch the parent either. The only thing that assumes the admin tag is complete is A-32's test 'keeps the tag an administrator always had' (object-visibility.test.ts ~1983), which asserts the tag's form (^W/"\d+"$), not that an admin 304 is correct after a child is added. A-32's own outcome admits the count 'changes with neither the object nor a grant'. No test asserts an admin 304 after a child create (conditional-get.test.ts covers settings, credentials and reparent only). Not ticketed and not in round 4. It also reaches every caller on an install with auth off, since all of them are visibility.everything there. The web client never reads childCount from the detail response (packages/web/src only declares it in api/types.ts:65), so there is no UI impact. Only API clients that revalidate are affected, and the stale value is a count. Low. It shares detailTag with restricted-etag-hidden-ancestor-oracle, but the cause is different (a missing input versus an over-broad one), so it is not a duplicate. The fix would need the A-32 admin-form assertion updated.

### GET /objects/:id/access/effective answers for hidden ids, returns the carve-out's id, and so lists every object inside a hole

- **Severity:** low (both verifiers). **Category:** security. **Introduced in:** `1932abe`, at `packages/core/src/api/routes/access.ts:85`.
