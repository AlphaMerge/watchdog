=============================================================================
P-194 asked whether creating objects gets slower as the installation fills up.

ANSWER: no effect is detectable, and the question was smaller than the noise.

-----------------------------------------------------------------------------
1. THE FILL SWEEP
-----------------------------------------------------------------------------

The same 5,000-object build into a database already holding N objects, run
ascending then descending so warm-up and fill can be told apart. Quiet
machine, conditions recorded by the run (P-192):

  already there     bulk up  bulk down  serial up  serial down
  0 objects           2.3 s      2.1 s     21.9 s       22.0 s
  5,000 objects       6.5 s      6.2 s     27.0 s       22.7 s
  10,000 objects      2.7 s      6.1 s     25.0 s       21.4 s
  20,000 objects      1.6 s      1.6 s     20.9 s       20.6 s

A fill effect would be a trend both directions agree on. There is none. The
fastest point for BOTH paths is 20,000 objects already present -- the most
filled -- and the two directions disagree at 10,000 (bulk 2.7 s up, 6.1 s
down). Whatever moves these numbers, it is not how full the database is.

An earlier sweep ran ascending only and produced a tidy-looking curve going
the wrong way (1.00x, 2.97x, 1.29x, 0.72x). That was ordering: the prefill
that creates the fill also warms the process, so more fill means more warm-up
immediately before the measurement. Sweeping both directions is what showed
it up.

-----------------------------------------------------------------------------
2. WHY THE QUESTION WAS UNANSWERABLE AS ASKED
-----------------------------------------------------------------------------

Four runs on 2026-09-08, all on a quiet machine, all with conditions recorded,
same code, same commit:

  serial, 3-sample median   20.9    22.0    23.2    25.7 s
  within-run spread          0.6     1.1     3.3     0.8 s
  bulk                       2.2     2.2     2.3     2.2 s
  8 in flight                6.5     7.2     6.7     7.1 s

The serial median moves 4.8 s across runs -- a fifth of the number -- while
bulk moves 0.1 s and eight-in-flight 0.7 s. The noise is proportional to the
round-trips: 5,000 sequential HTTP requests accumulate scheduling jitter that
one request does not.

So P-194's premise -- "about a third more into a populated database" -- came
from two points in two different runs, and a third of a build is inside the
scatter of the same build measured four times.

**The within-run spread understates the uncertainty badly.** One of these runs
reported 0.6 s of spread on a number whose true run-to-run range is 4.8 s. A
median over three samples in one process is precise about the wrong thing.

-----------------------------------------------------------------------------
3. WHAT THIS RETRACTS
-----------------------------------------------------------------------------

P-193 concluded that serial-into-empty (20.9 s) against serial-after-bulk
(27.9 s) showed "the seven seconds were 5,000 rows, not the per-request path".
The direction may well be right -- the populated readings do sit high -- but
the magnitude is not established: a single 20.9 against a single 27.9, when
the same measurement spans 20.9 to 25.7 unaided, is not seven seconds of
anything. That number is withdrawn; the structural point it rested on (the
variants used to share one database and were not comparable) stands, because
that was a fact about the code, not a measurement.

-----------------------------------------------------------------------------
4. WHAT TO DO WITH IT
-----------------------------------------------------------------------------

Nothing, for now, and deliberately. The budget is 30 s, the mean is around
23 s, and the run-to-run scatter is a couple of seconds. That is thinner than
it looks on any single run and wider than it looks on any single sample, and
the honest summary is that this case cannot resolve changes smaller than about
two seconds. The test now prints that in its own output so the next reader
does not have to find this file first.

The sweep is committed behind `MS_BENCH_FILL=1`, off by default: three minutes,
and the answer only changes when the write path does.

Raw output of both sweeps and the four runs follows.
