One case failed:

  creates a 5,000-object tree through the API inside its budget
      a serial build took 30.7 s against a 30 s budget

That case took 26.0 s on the quiet 2026-09-07 run -- 13% of headroom, the
thinnest margin in the suite, so a failure there is not obviously noise.

Most other cases also ran slower (conditional GET +28%, notification timers
+33%, schedule sweep +19%, process runner +46%), which makes contention a
plausible explanation. But the run moved in BOTH directions: clone came in
22% faster, the replay percentiles a little faster, and P-15 fully 20%
faster (404 s against 508 s) despite the stack being restarted underneath
it. A run that is 46% slower in one place and 20% faster in another is not
measuring the system; it is measuring the machine. It CANNOT distinguish
contention from a real regression, and must not be read as having cleared
-- or as having failed -- the tree build. A clean re-run is owed.

For the record on what changed since the clean run: P-189 added a pending-map
and a `disconnect` method to the probe endpoint, P-190 was prose only, and
P-191 removed one string from a Set. None of them are on the object-create

CORRECTION, added the same day (P-192). The conditions recorded above are the
HOST's, and the tests do not run on the host. They run inside the Docker
toolchain container, and at the moment this correction was written the two
disagreed by a factor of twenty: macOS reported a load average of 25.50 while
the VM the tests run in reported 1.29 across the same eight CPUs.

So `whatsbot-runner-fixed at 30.60%` -- a third of one core out of eight, from
inside the VM -- is not evidence of a contended test, and the load averages
near 20 are not either. This file records a busy Mac. It does not establish
that any of that busyness reached the measurement, which leaves the tree-build
failure unexplained rather than explained by contention.

One thing IS established, and narrowed. `ms-server` shares the VM and the
PostgreSQL instance with the suite, so it is the one contender that certainly
reaches it. Container start time puts it at 12:13:22 local, against a run
window of 12:08:07 to 12:18:35 -- five minutes in. Working from the case
durations in order, the tree build ran at roughly 12:10 and finished before
`ms-server` came up; P-15, at 404 s, ran with it up for most of its length.
The note above that the restart contaminates P-15 in particular is therefore
right, and it does not extend to the tree build.

Nothing here changes the conclusion: the run cannot distinguish noise from a
regression, no budget moves, and a clean re-run is owed. What changes is why.
It is not that the machine was too busy to measure -- it is that nobody
recorded the conditions that govern the measurement. `P-192` makes
`npm run test:perf` print them itself.
