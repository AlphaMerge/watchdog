## `S-21` — PowerShell quoting and a clipped secret

### windows.service escapes only ASCII ' when embedding the service name in PowerShell, so a typographic quote runs arbitrary PowerShell on the probe

- **Severity (verified):** high. **Category:** security. **Introduced in:** `be4258a`, at `packages/sensors/src/types/windows-shared.ts:38`.
- **Scenario.** This applies to the full profile, which is what release 1.1 ships (Windows types are only withheld from v1). An account that may write a sensor creates a windows.service sensor with service = "x’; Start-Process calc; ’". The name contains U+2019, which is not an ASCII apostrophe. windows-service.ts:65 builds the filter Name = 'x’; ...’', doubling only U+0027. windows-shared.ts:38 wraps that in -Filter '...' and again doubles only U+0027. PowerShell's tokenizer treats U+2018 to U+201B as single quotes, so the U+2019 ends the -Filter string and `Start-Process calc` runs as its own statement. The injected command runs inside buildScript's try block, in powershell.exe/pwsh spawned by the probe under the probe's service account. That process holds $env:MS_WIN_PASSWORD for the check's Windows credential, and the account can read the probe's identity key and config. This is the exact outcome T-19 and S-19 exist to prevent: creating a sensor becomes running any command as the probe.
- **Why the verifier kept it.** The service name goes into the PowerShell script text as it is. Both escaping layers double only U+0027. PowerShell's tokenizer (5.1 and 7, CharExtensions.IsSingleQuote) also treats U+2018, U+2019, U+201A and U+201B as single-quote characters, so any of them closes the -Filter string. The schema has only minLength/maxLength, and I found no other guard on the value: no pattern, no core-side check, no handling of U+2018-201B in packages/. -EncodedCommand (UTF-16LE) carries the character through intact. The attacker does not even need a separate statement. A payload such as x’ $(Start-Process calc) ’ puts a subexpression in Get-CimInstance's own argument list, and PowerShell evaluates that before the cmdlet runs, so $ErrorActionPreference='Stop' and the try/catch do not help. The code runs in powershell.exe under the probe's service account, with $env:MS_WIN_PASSWORD set when a credential is attached. Any account allowed to create or edit a sensor can reach this. It is not covered by S-19 (exe.script env/cwd) or S-20 (ping argv), and no open ticket covers it. Severity stays high for the full profile. The v1 build (1.0) is not exposed, because WITHHELD_FROM_V1 keeps windows.* out of the catalogue (packages/sensors/src/index.ts:218-225). Release 1.1 ships this type. The only other queryCim filter (windows-volume) is a constant, and host and credentials travel in the environment, so windows.service is the only injectable input.
- **Trace.** POST sensor create/update -> SensorCatalogue.validate against windows-service.ts:35-45 (string, minLength 1, maxLength 256, no pattern) -> probe CheckPool worker -> catalogue-registry execute -> windows-service.ts:61-66 queryCim(..., `Name = '${service.replace(/'/g, "''")}'`) -> windows-shared.ts:38 ` -Filter '${filter.replace(/'/g, "''")}'` -> windows-shared.ts:39-42 snippet -> powershell.ts runPowerShell -> envelope.ts:74-99 buildScript interpolates the body raw into `$MsData = & { ... }` inside try -> powershell.ts Buffer.from(script,'utf16le') base64 -> runProgram(powershell.exe -EncodedCommand) with env holding MS_WIN_PASSWORD.
- **Suggested fix.** Keep the value out of the script text. Pass the filter (or the service name) in the environment, e.g. MS_WIN_FILTER, the same way ENV_HOST and ENV_USER already travel, and have the snippet use -Filter $env:MS_WIN_FILTER. The minimal alternative is to escape every PowerShell single-quote character at both layers: replace(/['‘-‛]/g, (q) => q + q). Neither closes WQL-level quoting, where backslash is the escape; that only lets the query match a different service, not run code. Adding a pattern on `service` such as ^[A-Za-z0-9_.\- $]+$ is also reasonable defence in depth.
- **A test that would have caught it.** In packages/sensors/test/windows-sensors.test.ts, run windows.service with a fake interpreter that captures the decoded -EncodedCommand. Use service names containing each of U+0027, U+2018, U+2019, U+201A and U+201B, followed by '; $(evil) ;'. Assert that the captured script contains no single-quote character that is not doubled, or, with the env-var fix, that the service name does not appear in the script at all and arrives only as MS_WIN_FILTER.

### exe.script clips stderr to 300 characters before the catalogue scrubs, so a secret spanning the cut leaks its prefix

- **Severity (verified):** low. **Category:** security. **Introduced in:** `61281fe`, at `packages/sensors/src/types/exe-script-shared.ts:290`.
- **Scenario.** An exe.script sensor with secret = a 40-character API key runs a script that fails and prints a long last line, over 300 characters, containing the key at offset 280, for example a verbose client error that includes the header it sent. runScript's tail() joins the last three lines and cuts at 300, so the message holds the first 20 characters of the key followed by '…'. SensorCatalogue.execute then scrubs only exact whole values, finds no match, and the prefix goes to the state log, notifications and every reader of the sensor. The program printed the secret whole. The split is made by our own clipping, which runs before the scrub. powershell.ts tail() and the ssh clip() have the same order.
- **Why the verifier kept it.** The mechanics are as described. tail() joins the last three lines and cuts at 300 characters. The cut text is put into ScriptError at exe-script-shared.ts:177, and the catalogue's scrub runs only afterwards (catalogue.ts:203). scrubSecrets does only whole-value split/join, so a secret straddling position 300 leaves its prefix before '…'. The same order holds for the 400-character cut in powershell.ts tail(). The S-19 note (TASKS.md:481-486, secrets.ts header) says the scrub 'cannot catch an encoded or partial secret', which is close to this. But that limit is written about what the program does to the secret (encoded, split, hashed). This is our own clipping turning a whole secret into a partial one before the choke point sees it, and moving the scrub ahead of the clip closes it. Low: the program must print the secret, it must land exactly on the cut, and only a prefix leaks. Readers are those who can read the sensor, and notification recipients.
- **Trace.** exe.script check -> catalogue.ts execute -> type.execute -> exe-script-shared.ts runScript -> runProgram -> non-zero exit -> :177 throw new ScriptError(`${program} exited with code N${tail(run.stderr)...}`) -> :286-290 tail: last three lines joined, last.slice(0, 300) + '…' -> catalogue.ts:203 throw scrubbedError(error, secrets) -> secrets.ts scrubSecrets out.split(secret).join(marker) finds no whole match -> the prefix stays in the message, which goes to the state log and notifications.
- **Suggested fix.** Scrub before clipping. The catalogue already computes `secrets` via secretsOfCheck. Expose a scrub on the CheckContext, e.g. context.scrub(text), built from those secrets in SensorCatalogue.execute. Then have runScript (and powershell.ts/ssh clip) apply it to stderr/stdout before tail(). Alternatively, and cruder, make the catalogue also remove any trailing prefix of length 4 or more of a secret that sits immediately before '…'.
- **A test that would have caught it.** In packages/sensors/test, an exe.script test with secret = a 40-character value and a fixture script that exits 1 after printing one stderr line of 280 filler characters followed by the secret. Assert that the thrown or recorded message contains no substring of the secret of length 4 or more (not just that the whole value is absent).

## `A-44` — Notification rows name accounts and carry program output

### A non-admin writer can learn account logins, group names and group membership through POST /templates/:id/test

- **Severity (verified):** medium. **Category:** security. **Introduced in:** `269a3de`, at `packages/core/src/notifications/recipients.ts:164`.
- **Scenario.** M-20 makes GET /accounts and GET /groups ADMIN because "a list of logins is a list of what to try passwords against". A readwrite, non-admin account does this instead: POST /templates (WRITES) with method email and up to 200 recipients `{kind:'user', value:'1'}`…`{kind:'user', value:'200'}` plus `{kind:'userGroup', value:'N'}` entries, then POST /templates/:id/test with a sensorId it can read. The answer's `detail` ("; not sent to …"), or `error` ("nobody to send to: …"), lists every skipped recipient. An unused id reads `user 57 (no such account)`. A real one reads `user "alice" (disabled)`, `user "bob" (may not see this sensor)`, or `"carol" in group "NOC" (no email address)`. So the writer learns which account ids exist, their logins, group names, who is in each group, and whether a given account may read a given sensor. Those are the account list, the membership list and the effective-rights answer, all of which are ADMIN.
- **Why the verifier kept it.** A non-admin writer can save a template naming arbitrary user and group ids. Template validation checks only that each value is a decimal id. It does not check that the account or group exists, or that the caller is an admin. M-20's 'only an administrator picks users and groups' is enforced only in the web editor. The writer then calls POST /templates/:id/test with a sensor it can read. EmailTransport.send runs the RecipientResolver, and every skipped recipient is named with the login and group name. An unused id reads 'user N (no such account)'. A real account reads 'user "login" (disabled | no email address | may not see this sensor)'. A group member reads '"login" in group "name" (...)', and an empty group reads 'group "name" (no members)'. That text comes back in the report's detail ('; not sent to ...') or, when nobody resolves, in error ('nobody to send to: ...'). So the writer learns which ids exist, logins, group names and membership, and whether an account may read a given sensor. M-20 made the account and group lists ADMIN precisely because 'a list of logins is a list of what to try passwords against'. Recipients who are enabled, have an address and may read are mailed silently and not named, so enumeration is partial. Still, the logins and group memberships of everyone who is skipped do leak. Two preconditions apply: an SMTP relay must be configured (email.ts:110-119 returns before resolving otherwise), and the send is audited as template.tested and actually mails permitted recipients. That noise does not stop the leak. A-16 lists this route only for echoing the rendered message (tree names), not for recipient names, so it is not ticketed. M-19 decided skipped recipients are named in the delivery result for whoever configured the template. It did not decide that a non-admin may probe arbitrary ids.
- **Trace.** api/routes/templates.ts:533 POST /templates is config WRITES. notifications/templates.ts:~636-652 #parse checks recipients: user and userGroup only need recipientId(value) !== null (line 646), with no existence or role check. templates.ts:492-500 POST /templates/:id/test is `every(WRITES, onBodyObject('read','sensorId',{optional:true}))`. test-send.ts:~100-133 loads the template and calls transport.send with recipients: template.recipients and about: [sensorId]. delivery/email.ts:125-130 calls resolve(), then describeSkipped, then error `nobody to send to: ${skipped}`. email.ts:152 returns {ok:true, detail, skipped}. recipients.ts:147-151 consider() gives skip 'disabled' / 'no email address' / 'may not see this sensor' with who = `user "${login}"`. recipients.ts:164 gives `user ${id}` 'no such account'. recipients.ts:168-176 gives group "name" 'no members' and `"${member.login}" in group "${group.name}"`. test-send.ts:152-157 builds detail `${detail}; not sent to ${skipped}` and error = result.error, returned to the caller. routes/accounts.ts:70 GET /accounts is ADMIN, and GET /groups is ADMIN.
- **Suggested fix.** Enforce M-20's decision on the server. In TemplateService create/update, refuse a user or userGroup recipient from a caller who is not an admin unless that same {kind, value} was already on the stored template (M-20 lets writers keep and remove existing rows). The routes need to pass whether the caller clears admin (clears(request,'admin')). As defence in depth, have NotificationTester.send describe skipped account and group recipients by id and reason only when the caller is not an admin. Or leave out their names entirely: 'N recipients were not sent to'.
- **A test that would have caught it.** Write an access-matrix / templates test. A readwrite non-admin POSTs /templates with recipients [{kind:'user', value:<id of a disabled account>}, {kind:'userGroup', value:<group id>}]. Assert a 403/validation refusal. Separately, an admin-authored template with such recipients is test-sent by a non-admin writer. Assert that the response detail and error contain neither the account's login nor the group's name. An administrator's test send still names them.

### Execute-program notifications send the program's stderr, which may hold secretArgs, to the test-send answer, last_error and the journal without scrubbing

- **Severity (verified):** low. **Category:** security. **Introduced in:** `28472e4`, at `packages/core/src/notifications/delivery/program.ts:302`.
- **Scenario.** An operator's notification template runs send-sms.sh with secretArgs ["<api-key>"]. secretArgs is writeOnly, so no route returns it. The script uses `set -x` or prints its usage on error, as shell scripts commonly do, so stderr contains '+ curl -H "X-Key: <api-key>" ...'. The script exits non-zero. classify() puts excerpt(run), the last stderr line, into the delivery error. test-send returns that error to the caller (test-send.ts:157), and the dispatcher stores it in last_error. #log writes the whole stdout and stderr to the journal. So a value the API promises never to return comes back to anyone who can run a test send or read delivery health. S-19 fixed exactly this class for sensor checks ('a script's last lines of output ... may include the password'), but nothing scrubs it on the notification side, and the N-10 outcome claims 'nothing reaches the journal by accident'.
- **Why the verifier kept it.** secretArgs is appended to argv. The program's last stderr line (or stdout line), up to 200 characters, goes unscrubbed into DeliveryResult.error. test-send returns that to the caller, and the dispatcher stores it in last_error, which /notification-health and /notification-requests serve as lastError. #log writes stdout and stderr to the journal in full. The comment at that spot says secretArgs must never reach the journal, and that is exactly how it gets there. git grep finds no scrub function anywhere in packages/core/src. This is not A-40, which is about re-pointing where a stored secret is sent, not echoing it back, and N-10 accepted only /proc cmdline exposure. It is low because it depends on an operator-installed program printing its own secret argument (set -x, usage text, a verbose client error). The readers are accounts with template write rights (test-send needs the WRITES bar) and readers of notification health, not arbitrary users.
- **Trace.** POST /templates/:id/test (packages/core/src/api/routes/templates.ts:492, WRITES bar) -> test-send.ts #attempt -> delivery/program.ts send: :75 readArgs(settings['secretArgs']) appended to args -> runProgram -> :96 this.#log(...) -> :166 { stderr: run.stderr } logged whole -> classify :274/:286 error = `${name} exited N${excerpt(run)}` -> :302-306 excerpt returns the last line, up to 200 characters, unscrubbed -> test-send.ts:157 error: result.error in the response. In the queued path, dispatcher.ts:594 sets last_error = $2 -> notifications.ts:51/142 lastError in the API response.
- **Suggested fix.** In ProgramTransport.send, collect the substituted secretArgs values of 4 or more characters. Run run.stdout and run.stderr through a scrub (the same exact-value replacement as @ms/sensors scrubSecrets, moved to @ms/shared) before both #log and classify. That is one choke point before the output is used anywhere.
- **A test that would have caught it.** A core delivery test with a program in the programs directory that writes its last argument to stderr and exits 1. Configure secretArgs ['s3cr3t-key']. Assert that the DeliveryResult.error, the test-send report's error and the logged stderr contain the marker and not 's3cr3t-key'.

## `A-45` — A-29's vouching: auth off, a stale sight, a settle that never retries

### With requireAuthentication off, a logged-in non-admin's write records an account voucher, and the sweep then withholds the sensor (Core Health included)

- **Severity (verified):** medium. **Category:** correctness. **Introduced in:** `ce63373`, at `packages/core/src/api/authorization.ts:372`.
- **Scenario.** The installation runs with api.requireAuthentication=false (the supported upgrade state). An operator account 'ops' (readwrite, in no administrators group, no grants, since grants do nothing with the layer off) logs in, which /auth/session supports, or calls with a Bearer token, and saves a Sensor Factory's formula or a Core Health sensor. registerAuthentication still sets request.principal when required=false, so writerFor returns `{kind:'account', userId: ops}`. The write-time check passes, because the sight is EVERYONE. recordVoucher stores vouched_by='account'. On the next 30 s sweep, SensorVouching resolves ops's real grants through objectAccess.visibilityFor, and it knows nothing about the auth layer being off. The named sensors, and the root for Core Health, are not visible, so the sensor is withheld: Unknown/access with channels gapped. Core Health stops reporting, which is self-monitoring switching itself off. Migration 059 does the same on upgrade for any sensor last written by a logged-in user on an auth-off install.
- **Why the verifier kept it.** With api.requireAuthentication=false the authorisation layer is off: registerAuthorization gives every request the EVERYONE sight. The authentication hook still resolves a session cookie or bearer token into request.principal before it returns on !required. Login is still possible because /auth/login is ALWAYS_PUBLIC. writerFor only checks `principal === undefined`, so any logged-in or token caller gets an account voucher instead of the installation one. That contradicts writerFor's own doc, the Writer doc in sensor-reads.ts:43-45, and migration 059's header, which all say an installation with the layer off vouches as the installation. The write-time check passes because `sees` resolves through the EVERYONE sight. recordVoucher then stores vouched_by='account'. The sweep's sight is AccessService.visibilityFor with no knowledge of `required`, and it withholds the sensor (Unknown/access, channels gapped) when that account's real grants do not cover what the sensor names. It does the same when the account is later disabled or deleted (WITHHELD.disabled/deleted). The deleted or disabled case needs no special grant setup, which is why this stays medium. For a readwrite account in the default Users group, migration 033's read-on-root grant usually covers the named ids and the Core Health root bar. So the lost-read case needs non-default grants, but the deleted or disabled case happens on an ordinary auth-off install. Migration 059's backfill has the same gap: any sensor whose last params write was by a logged-in user on an auth-off install becomes account-vouched. The decided A-29 behaviour is 'auth-off means the installation vouches'. The code does that only for anonymous callers, so this is the implementation missing its decision, not the decided per-sensor Unknown fan-out.
- **Trace.** packages/core/src/api/authentication.ts:152-175 (principal set from bearer/session) -> authentication.ts:177 `if (!options.required) return;` -> packages/core/src/api/server.ts:633-636 registerAuthorization({required: auth.required}) -> packages/core/src/api/authorization.ts:447-455 (layer off: sight = EVERYONE) -> authorization.ts:357-379 writerFor: principal defined -> `voucher: {kind:'account', userId}` (372), sees -> EVERYONE -> packages/core/src/objects/service.ts:1807 voucherOf(writer) -> assertMayName passes -> service.ts:1810 repo.recordVoucher (repository.ts:1047-1054 UPDATE sensor_config SET vouched_by='account') -> sweep: packages/core/src/main.ts:508-514 SensorVouching sight = objectAccess.visibilityFor (no `required`) -> packages/core/src/objects/vouching.ts:237-251 (deleted/disabled/lostRead refusals; bar -> rootId asked) -> settle -> Unknown/access. - **Suggested fix.** In writerFor, when the layer is off (sights.get(request) is undefined or its `fresh === EVERYONE`), return the user writer with `voucher: INSTALLATION_VOUCHES` so the audit still names the account. Log in as a non-admin account whose groups have no grant on the root (or disable it afterwards) and PUT a Sensor Factory formula or Core Health params. Assert sensor_config.vouched_by = 'installation'. Then run SensorVouching.refusals over it and assert it is not withheld, including after the account is disabled or deleted.

### A pre-revoke sight can be cached under the post-revoke epoch, so a revoked voucher keeps publishing until the next epoch bump

- **Severity (verified):** low. **Category:** security. **Introduced in:** `ce63373`, at `packages/core/src/objects/vouching.ts:335`.
- **Scenario.** The factory, Probe Health and Core Health sweeps share one SensorVouching and are all started on the same 30 s period, so they run in phase. After any grant change (epoch E), sweep A resolves an account's sight afresh (#sights is empty) through this.#sight(...). While that query is in flight, an admin revokes the account's read on the sensor a factory names (epoch E+1). Sweep B's refusals() reads E+1, clears #sights/#readable and sets #epoch=E+1. A's sight, computed from the pre-revoke grants, then lands in #sights via `this.#sights.set(key, sees)`. Every later sweep reads epoch E+1 == #epoch, keeps the cache, and evaluates visibleAmong with the stale grants. The factory keeps republishing the revoked sensor until some unrelated grant, membership or move bumps the epoch, which on a quiet install may be never.
- **Why the verifier kept it.** SensorVouching is one instance shared by the factory, Core Health and Probe Health sweeps. Then A's pre-revoke sight is stored under E+1. It stays there if B did not also resolve and store that same account's sight after A. Later sweeps see epoch == #epoch, keep the cache, and answer visibleAmong for ids not yet in `known` with the stale boundaries. The factory keeps republishing a sensor its voucher can no longer read until an unrelated grant, membership or move bumps the epoch. The window is narrow (a query round trip overlapping a grant change and another sweep's epoch read), hence low. It still breaks A-29's per-epoch cache contract, and nothing else at HEAD stops it: no lock serialises the sweeps, and visibleAmong does not re-check the epoch.

### A failed voucher settle is never retried: a withheld sensor keeps its old stored state (Up, or Down with its alarm still running) for the whole time it is not evaluated

- **Severity (verified):** low. **Category:** false-history. **Introduced in:** `ce63373`, at `packages/core/src/objects/vouching.ts:281`.
- **Scenario.** An account's read on a factory's source is revoked. On the next factory sweep, refusals() returns the factory and settle('factory', ...) updates #withheld and #byOwner. Then the reevaluate transaction fails (a transient DB error, a lock or serialization failure, or a dropped connection), and the catch only logs. On the next sweep `before` already contains the sensor, so entered/left/reworded are all empty and settle returns before re-deciding anything. The factory is skipped every sweep and ingests no result, so applyResult never re-decides it either. sensor_runtime and sensor_state keep the pre-withholding state indefinitely. If that was Up, uptime counts it as monitored Up while nothing is evaluated. If it was Down, its Down alarm is never suspended, so escalation and repeats keep paging for a sensor nobody is evaluating. Reachability (P-80/P-90) and ClockFreeze both undo their set when the write fails; this does not.
- **Why the verifier kept it.** SensorVouching.settle commits the new withheld set and the #byOwner entry before the transaction runs. Its catch only logs and returns 0, and the comment there claims the next sweep's settle will read the set again. It will not: on the next sweep `before` already holds the sensor, so entered/left/reworded are empty and settle returns at the `changed.length === 0` guard before any reevaluate. The factory sweep skips a withheld sensor (`continue`) and ingests nothing for it, so applyResult never re-decides it either. ClockFreeze (clock-freeze.ts:201-202) and ProbeReachability (P-80/P-90) both roll the set back on failure; this does not. The released direction (`left`) heals on the next ingested result, but the withheld direction (`entered`) does not. I grade it low, not medium. It needs the settle transaction to fail right after refusals() succeeded against the same DB, which is a narrow window, and a restart heals it. The effect, while it lasts, is a false history.

- **Scenario.** An operator has write on device X. A sibling device H under the same group is carved `none` for them. ## `A-47` — Host, throttle, proxy range and idle timeout

### The Origin check compares Origin with the request's own Host, so a DNS-rebinding page passes it on the stream and on every write when authentication is off

- **Severity (verified):** medium. **Category:** security. **Introduced in:** `c9a7b0a`, at `packages/core/src/api/hardening.ts:215`.
- **Scenario.** The core runs with api.requireAuthentication=false on its default bind, 127.0.0.1:8080. An operator on that host opens http://evil.example:8080/. The page's name first resolves to the attacker's server, then is re-pointed to 127.0.0.1. The page runs new WebSocket('ws://evil.example:8080/api/v1/stream') and fetch('/api/v1/...', {method:'POST'}). The browser sends Origin: http://evil.example:8080 and Host: evil.example:8080. refusalFor finds originHost === host and lets both through. The page reads a snapshot of every sensor, streams live changes, and can write configuration. To the browser these calls are same-origin, so every GET response is readable too. A-36 says the handshake check is 'the only thing between another site and the feed' with authentication off. It only proves that Origin and Host agree, and a rebound name makes them agree.
- **Why the verifier kept it.** The Origin check trusts the request's own Host header, and no code anywhere checks that Host names the core. The only read of headers.host in packages/core/src is hardening.ts:215, and there is no allowed-hosts setting. A rebound name makes Origin and Host match, so refusalFor lets the request through. With api.requireAuthentication=false, both the authentication hook (authentication.ts:177) and authorization (authorization.ts:447) stand down, and the page gets anonymous full access to the API: the stream, every write, and every GET, since GETs are same-origin to the browser and are never Origin-checked. With authentication on, the session cookie is scoped to the real host name and is not sent to the rebound name, so the attack only works with auth off. That is non-default (schema.ts:842 defaults to true), but it is a documented operator choice (schema.ts:397-401). server.ts:596-597 and hardening.ts:169-170 claim this check is the only protection in that mode, and it does not hold. No decided item or open ticket covers it: A-36 decided only the no-Origin case. I keep medium rather than raising it, because it needs a non-default setting and a browser that can reach the core, and some browsers' local-network-access protections partly mitigate it.

### The login throttle keys on the exact address and its per-account delay does not limit parallel attempts, so rotating addresses in an IPv6 /64 gives unbounded guessing, now per browser behind a trusted proxy

- **Severity (verified):** medium. **Category:** security. **Introduced in:** `c9a7b0a`, at `packages/core/src/auth/throttle.ts:90`.
- **Scenario.** An attacker on an ordinary IPv6 connection (a /64) sends 200 concurrent POST /auth/login for 'admin', each from a different address in the prefix. Without a proxy request.ip is the socket address. Behind a proxy listed in api.trustedProxies (A-36), request.ip is each browser's own address. Every check() sees by_address = 0, below maxPerAddress = 20, so none is refused. Every request runs argon2 verification. The per-login delay (min(byLogin*500, 5000) ms) is only a sleep before that one request's answer, so it does not limit concurrency. Throughput is set by argon2 CPU, not by the throttle. The code's claim that 'a guessing run collapses' holds only for serial attempts. Before A-36 a proxied install collapsed every browser into the proxy's one address, which at least capped the whole world at 20 failures per 15 minutes.
- **Why the verifier kept it.** Both limits a login attempt meets are keyed on the exact address. The per-address count in the throttle filters on remote_address = $2 (throttle.ts:90), and the general rate limit uses the key ip:${request.ip} (hardening.ts:368). Neither aggregates an IPv6 prefix, so each fresh address in a /64 starts at zero. The per-account defence, which the file's own design says is the answer to a spread-out spray (throttle.ts:7-20), is only a sleep before that one request's answer (routes/auth.ts:159, throttle.ts:131-133). It never refuses and never serialises, so concurrent attempts each get a full argon2 verification, and throughput is bounded only by CPU. The waitOut comment says the delay 'costs a guessing run its throughput', which holds only for a serial client. There is also a check-then-record race: check() reads the counts before any of a concurrent batch has been recorded, so even a single address gets one burst larger than maxPerAddress. The same weakness covers TOTP code guessing (routes/auth.ts:188-192). A-39 (rate limit not configurable) and A-36 (XFF spoofing) do not cover address rotation or concurrency. Medium: this is online guessing against a login, and the admin login is usually known.

- **Severity (verified):** low. **Category:** security. **Introduced in:** `c9a7b0a`, at `packages/shared/src/config/schema.ts:1177`.

## `P-240` — The ownership cache can keep a moved sensor's old probe

## `M-23` — A withheld sensor releases or downs what depends on it

### Withholding a sensor that is a dependency master releases its dependents at once, and each one then pages Down: one grant edit, N alarms

- **Severity (verified):** medium. **Category:** alarm-volume. **Introduced in:** `ce63373`, at `packages/core/src/objects/vouching.ts:296`.
- **Scenario.** A Sensor Factory (e.g. 'WAN up = ping1 OR ping2') or a Probe Health sensor is the master for 40 branch-office sensors. The WAN is down, so the master is Down and pages once, and the 40 are paused_by_dependency. An admin then revokes a grant that the master's voucher relied on. settle() re-decides the master to unknown/access, then calls dependencies.recompute(). applyPauses' `holding` seed only counts masters in down/down_acknowledged or with a pending dependency_clear_at. recompute goes through #settle and not react/markRecoveries, so no recovery delay is set and dependency.delaySeconds is skipped. All 40 dependents are released in the same transaction and resume to unknown/scan. Their next scans read Down because the WAN is still down, and a Down trigger arms and pages for each. A-29 says withholding must not turn a grant edit into one alarm per sensor, and here the outage those sensors measure is unchanged.
- **Why the verifier kept it.** The path is real at 21e5d84. A Down master that becomes withheld is re-decided to unknown/access, and settle then calls dependencies.recompute. recompute goes straight to #settle and never through react()/markRecoveries, so no dependency_clear_at is set and dependency.delaySeconds is never applied. The applyPauses `holding` seed counts only masters in down/down_acknowledged or with an unexpired dependency_clear_at, so a master in unknown/access stops holding at once. Every dependent is released to unknown/scan in the same transaction. Their next scans report the continuing outage as Down, and each Down trigger arms per dependent. The masters that can be withheld are exactly the core-evaluated types (Sensor Factory, Probe Health, Core Health), and Probe Health or a WAN factory as a master is the WORKFLOW §5 pattern. Disabling or deleting the account that wrote such a master, which is routine when someone leaves, triggers it. The release is deliberate in the vouching.ts:294-296 comment, borrowing P-135's reasoning. However, no ticket decides it for A-29. A-29's own rationale ('one grant edit must not become one alarm per sensor') and the dependency rule that recovery waits the configured delay are both broken, and A-29's notification test counts only the withheld factories, not their dependents. This is not P-135 (a lost probe) and not M-22 (Unknown fan-out). It only bites when the master is Down at the moment it is withheld, so I grade it medium.

- **A test that would have caught it.** Scenario test in sensor-vouching.test.ts (per the M-17 rule). A Sensor Factory master is Down and holds 20 dependents under a Down trigger. Revoke the voucher's read on the factory's source and run a factory sweep. Then ingest 'error' results for all 20 dependents. Assert they are still paused_by_dependency and that notification_request gains zero rows beyond the master's original alarm.

### A withheld factory's channels are removed from the sweep's inputs, so a factory built on it, vouched by another account, goes Down on the next sweep and pages

- **Severity (verified):** medium. **Category:** alarm-volume. **Introduced in:** `ce63373`, at `packages/core/src/factory/service.ts:160`.
- **Scenario.** Factory B (vouched by operator X) sums interfaces in a branch. Factory C (vouched by an admin, who can still read B) computes `#B.total * 8`, and C has a Down trigger. X loses read on one of B's interfaces. B is withheld as intended (Unknown/access, no page). In the same sweep, B's channel keys have already been removed from `inputs.channels` and B is skipped. C's formula evaluates to null, and with every channel gapped C records outcome 'error' ('none of this Sensor Factory's formulas could be evaluated'). C goes Down, its trigger pages, and sensor_state records a Down for C, though nothing either factory measures has failed. `inputs.up` also reads B as not-up, so status-based formulas flip the same way. One grant edit becomes a Down alarm and a Down history row on every factory downstream of the withheld one. That is what A-29's 'Unknown, never Down' rule was meant to rule out, and the missing data becomes a Down.
- **Why the verifier kept it.** The path holds at 21e5d84. The factory sweep deletes every sensor's own channel keys from the shared inputs map before checking whether it is withheld; it does this on purpose so a reader sees a gap (the comment at service.ts:157-159). A withheld B is then skipped. A downstream factory C that reads only B's channels finds every formula evaluating to null. With readings.length === 0, C gets an 'error' result, which is ingested and decided as a failed scan, and so goes Down after its failure policy; its Down trigger pages. Status formulas read B's unknown/access row as not-up (service.ts:407), so they flip the same way. C's own voucher check only asks whether C's voucher can read B, so an admin-vouched C is not withheld and nothing turns the upstream withholding into Unknown for C. A grant edit on an account that has nothing to do with C writes a Down row into C's history and pages. A-29 and administration.md say that must not happen ('Nothing measured has failed... must not become one alarm'). Mitigating: this is the general factory rule (all inputs missing means a fault of its own), which applies equally when an upstream sensor is Unknown for other reasons. The alarms are one per downstream factory, not one per sensor the account wrote. No decided or open ticket covers it, and A-29's tests do not exercise a factory over a withheld factory. Medium.

## Refuted: a non-admin clone carries other groups' grants into a new branch

The write-authority area reported that `POST /objects/:id/clone` copies every group's `object_access` rows on the copied objects (`repository.ts:1678-1690`). An operator with write on a device and on a target branch can therefore put another group's `write` grant inside a branch that group had no right in, which is an act that otherwise needs ADMIN.

The verifier refuted it as a defect, because it is what `A-35` decided. `A-35`'s outcome says the copied objects' grants, every group's, travel with them, and each copy is audited as `grant.set` by the cloner. `administration.md` says the same thing, and the `A-35` test asserts that a positive grant travels. No new right is minted: a group only holds, on the copy, a right it already held on the source.

**The question is left open, not closed.** Should a non-admin's clone carry positive grants for other groups, or only their `none` carve-outs, which were the reason `A-35` copies grants at all? That is a change to a decision, so it needs a decision, not a fix. The credential part of the scenario, a copy whose host is changed while it inherits the branch's credentials, is `A-41`'s.
